# CalSync 개발 계획서 (v0.1)

- 작성일: 2026-11-11
- 상태: 초기 기획 / 기술 검증 전
- 목표: 지정된 Google Calendar를 안전하게 공유하고, 외부 접속자가 일정 생성 정보 및 삭제 요청을 제출하며, 접속자 PC의 JSON 일정 데이터를 추후 자동 동기화할 수 있도록 한다.
- 원칙: **조회 / 변경 요청 / 실제 Google Calendar 반영을 분리**하고, Menlo Security 정책을 우회하지 않는다.
- 이 문서는 제안 설계이며 확정 요구사항이나 구현 완료 상태를 의미하지 않는다.

## 1. 요구사항 및 범위

### 1.1 확인된 요구사항

1. 접속자는 **Menlo Security Browser service**를 통해 웹 서비스에 접속한다.
2. 서비스 운영자가 설정한 **특정 Google Calendar**의 이벤트를 접속자에게 보여준다. 임의의 다른 캘린더로 확대 조회할 수 없어야 한다.
3. 접속자는 **신규 일정 생성에 필요한 정보**를 전달할 수 있다.
   - 제목
   - 시작 일시 / 종료 일시
   - 장소
   - 내용 / 설명
   - 참석자
   - 메모
4. 접속자는 기존 일정에 대해 **삭제 요청**을 할 수 있다.
5. 접속자 PC에서 실행되는 **데스크톱 자동 동기화 클라이언트**를 제공한다.
6. 접속자 측 일정 데이터는 **JSON 파일**로 제공될 예정이다.
7. **JSON 스키마 및 샘플은 프로젝트가 진척된 뒤 제공받아 확정**한다. 그 전까지 실제 형식을 가정하여 로직을 고정하지 않는다.

### 1.2 초기 버전(MVP)의 기능 경계

| 기능 | MVP | 정책 / 비고 |
| --- | --- | --- |
| 지정 캘린더 월/주/목록 조회 | 포함 | 서버가 허용한 calendar ID만 |
| 이벤트 상세 조회 | 포함 | 개인정보/민감정보 표시 정책 적용 |
| 신규 일정 등록 요청 | 포함 | 제출 후 검증, 상태 조회 |
| 기존 일정 삭제 요청 | 포함 | 실행과 요청 분리, 중복 방지 |
| 관리자 요청 검토/승인/거절 | 포함 | 기본적으로 승인 후 Google Calendar 변경 |
| 요청 이력 / 처리 결과 | 포함 | 감사 로그, 재시도, 실패 사유 |
| 데스크톱 JSON 감지 / 변경분 추출 | 포함 | 실제 형식은 어댑터로 별도 구현 |
| 데스크톱 자동 전송 | 조건부 | **승인된 네트워크/API 통신 경로가 있을 때만** |
| 자동 승인 모드 | 후속 옵션 | 신뢰된 클라이언트별 제한과 감사 로그가 선행돼야 함 |
| 기존 이벤트 일반 수정 | 제외 | v1에서는 생성/삭제 요청만 |
| 반복 일정 편집·복잡한 예외 | 후속 | 초기에 일회성 일정 우선 |
| 캘린더 간 범용 양방향 동기화 | 제외 | 무제한 복제 및 무조건적 상호 삭제 금지 |

**중요:** '신규 항목의 정보를 전달'한다는 요구는 우선 **생성 요청 제출**로 해석한다. 승인 절차를 생략한 즉시 생성은 운영자가 별도로 허용한 경우에만 활성화한다.

## 2. 전체 아키텍처

~~~text
[접속자 브라우저]
       |
       | 조직이 승인한 Menlo Security Browser 경유
       v
[Menlo 접근/보안 경계] -- 인증/접근 정책 --> [CalSync 웹 UI]
                                                |
                                                v
                                          [CalSync Backend/API]
                                            |        |        |
                                            |        |        +--> [DB: 요청/매핑/이력]
                                            |        +--> [승인/작업 큐]
                                            v
                                      [Google Calendar API]
                                            |
                                   [지정된 Calendar ID]

[접속자 PC JSON 파일]
       |
[CalSync Desktop Agent]
       |
       | 조직이 승인한 전용 API 경로가 있을 때만
       +----------------------------------------> [CalSync Backend/API]
       |
       +--> API 경로 미승인 시: 허용된 브라우저를 통한 수동 업로드 방식 검토
~~~

### 2.1 구성 요소

**웹 UI (접속자/관리자)**
- 조회: 월/주/목록 및 일정 상세, 기간 선택.
- 요청 입력: 생성 양식, 삭제 요청 버튼, 요청 처리 상태.
- 관리자 화면: 보류/승인/거절, 작업 이력, 캘린더 연결 상태.
- Menlo 호환성 확보를 위해 일반 HTTPS 폼 제출 및 폴링을 기본으로 한다. WebSocket, Service Worker, 파일 업로드, 쿠키, 리다이렉트는 실제 정책에서 검증한 후 채택한다.

**Backend/API**
- 접속자 인증 및 권한 검증, 요청 입력 검증, 승인 워크플로.
- Google Calendar 전용 어댑터 및 요청 실행 큐.
- 캘린더 이벤트의 조회 캐시/증분 동기화, 감사 로그.
- 데스크톱 에이전트 전용 API와 데이터 수신 엔드포인트.

**Desktop Agent**
- 지정 폴더의 JSON 파일 변화를 감시하고, 재시작 시 전체 재검증.
- JSON 변환 어댑터 → 내부 공통 이벤트 모델 → 생성/삭제 요청 비교.
- 변환 검증 결과, 이전 동기화 상태, 이벤트 ID 매핑, 전송 큐를 안전하게 저장.
- 사용자 환경에서 현재 상태/최근 실행/실패/수동 재시도를 확인할 수 있는 최소 UI 제공.
- 인증 토큰은 OS 보안 저장소에 보관하고 로그에 출력하지 않음.

**데이터 저장소**
- 허가된 사용자와 역할, 캘린더 구성, 요청, 상태 변경, 이벤트 매핑, 원본 버전, 감사 기록.
- 원본 JSON 및 참석자 등 민감 데이터는 꼭 필요한 범위만 저장하고 보존 기간을 설정.

## 3. Menlo Security 접속 및 보안 선결조건

Menlo Security가 웹 브라우저 접근을 매개한다고 해서 **데스크톱 프로그램의 임의 HTTP 통신까지 허용된다는 뜻은 아니다.** 자동화 구현 전에 다음을 실환경에서 확인한다.

1. Menlo 환경에서 CalSync URL 접속, 로그인/SSO, 쿠키, 화면 렌더링, 폼 POST, API 호출, 리다이렉트가 허용되는가?
2. 조직 정책상 읽기 전용 사이트로 분류되지 않는가? 입력/업로드/다운로드 정책은 어떠한가?
3. 데스크톱 에이전트가 사용할 수 있는 **공식적으로 승인된 API 경로**(별도 allowlist, 인증된 게이트웨이, 사내 프록시 등)가 있는가?
4. API 인증 방식(OIDC/OAuth, 승인된 디바이스 인증, mTLS 등), 사용자 식별 방식과 세션 만료 처리 기준은 무엇인가?
5. Google 계정 및 캘린더에 대해 API 접근, 외부 이벤트 공유, 참석자 정보 전송이 허용되는가?

**금지할 구현 방식:** 브라우저 쿠키/세션 탈취, Menlo 보안 통제를 우회하는 직접 접속, 숨겨진 브라우저 자동 조작, 허가되지 않은 네트워크 터널이나 프록시.

**조건부 대안:** 데스크톱 직접 API가 불허되면 자동 업로드는 막고, 조직이 허용하는 범위에서 사용자 주도 JSON 파일 업로드(가능한 경우) 또는 승인된 기업용 통합 채널을 검토한다. 두 경로 모두 막히면 무인 자동 동기화는 지원 불가로 명시한다.

## 4. Google Calendar 연동 설계

- Google Calendar API v3 사용.
- 관리자가 설정한 **단일 허용 calendarId**부터 시작한다. 캘린더 이름이 아닌 식별자로 고정하고 서버 측 접근 제어에 적용.
- 가능한 인증안: 운영자 OAuth 동의(Refresh Token 안전 보관) 또는 조직에서 허가된 Workspace 위임 방식. 사용 환경에 맞춰 확정.
- 권한은 최소 권한 원칙을 따르며 외부 접속자에게 Google 자격 증명/Refresh Token을 배포하지 않는다.
- 서버에서 이벤트 조회 후 표시 필드와 노출 범위를 통제한다.
- Google Calendar 이벤트 생성/삭제는 **승인된 백엔드 작업**에서만 수행한다.
- 메모 필드는 공개 설명(description)과 분리할지, 전용 내부 DB 또는 허가된 private extended property로 처리할지 결정한다. 기본적으로 일반 접속자에게 내부 메모를 노출하지 않는다.
- 참석자는 이메일 유효성/중복/권한을 검사한다. 초대 알림 발송(sendUpdates 등)은 운영 정책으로 정한다.
- 타임존은 IANA 식별자(기본 제안: Asia/Seoul)로 명시한다. 시작 < 종료, 종일 일정, DST 등을 검증한다.
- 목록 동기화는 초기 전체 조회 + syncToken 기반 변경분 추적을 권장한다. 페이지 처리, 삭제 이벤트 반영, 만료된 syncToken(HTTP 410) 재동기화를 구현한다.
- Google API 실패(429/5xx/인증 만료)에 대해 backoff, 재시도 제한, 관리자 알림을 둔다.

참고: [Google Calendar incremental synchronization](https://developers.google.com/workspace/calendar/api/guides/sync)

## 5. 주요 사용자 시나리오

### A. 캘린더 보기

1. 접속자: Menlo가 허용한 브라우저 경로로 CalSync 접속.
2. 인증 후: 서버가 해당 접속자에게 허가된 지정 캘린더만 조회.
3. 목록/기간/상세 정보 표시. 변경 요청 권한이 없는 사용자는 읽기 전용으로 표시.

### B. 일정 생성 요청

1. 사용자가 제목, 시작/종료, 장소, 설명, 참석자, 메모 입력.
2. 백엔드가 필수값/형식/권한/중복 요청을 검증.
3. 요청을 PENDING 상태로 저장하고 요청 ID 반환.
4. 관리자가 APPROVED/REJECTED로 처리.
5. 승인 시 작업 큐가 Google Calendar events.insert 수행.
6. 생성된 Google event ID를 요청/클라이언트 로컬 ID에 연결하고 SUCCEEDED 또는 FAILED로 기록.
7. UI/에이전트에서 결과를 조회하고 중복 처리하지 않음.

### C. 기존 일정 삭제 요청

1. 사용자는 **화면에서 확인한 event ID**의 삭제를 요청.
2. 서버는 캘린더 소속, 삭제 권한, 이벤트 버전/상태를 다시 확인.
3. 요청을 PENDING 상태로 기록. 기본 정책은 **자신이 제출한 일정만 삭제 요청 허용**; 그 외 일정 삭제는 관리자 명시 승인이 필요.
4. 관리자 승인 시 삭제 직전 최신 이벤트를 재조회하고 변경 충돌 여부를 확인.
5. 실제 삭제 후 결과/감사 기록 저장. 삭제 실패나 이미 삭제된 경우 멱등적으로 상태 정리.
6. 모든 일정에 대한 일괄 삭제 API는 초기 버전에서 제공하지 않음.

### D. 데스크톱 JSON 자동 동기화

1. 에이전트 시작 시 설정 폴더에 있는 JSON 파일을 읽고 형식 검증.
2. 형식별 Adapter가 공통 Event 모델로 변환. 스키마 미정 단계에서는 샘플/모의 어댑터만 구현.
3. 로컬 고유 ID 및 이전 동기화 스냅샷 비교 → 새 항목/변경/삭제 의도를 분류.
4. **새 항목**은 생성 요청으로 전송, 처리 결과 ID 매핑 저장.
5. **삭제**는 추후 정해진 명시적 삭제 마커(tombstone) 또는 사용자 확인 규칙이 있을 때만 요청 생성. 단순 파일 누락/빈 파일/파싱 실패를 대량 삭제로 간주하지 않음.
6. **수정**은 MVP에서 자동 반영하지 않고 변경 감지 알림/보류 처리. 추후 수정 요청 규칙 확장.
7. 에이전트는 네트워크 실패 시 로컬 큐에 보관하고 재시도. 재시도 후에도 같은 요청이 중복 생성되지 않도록 멱등 키 사용.
8. 에이전트 종료 후 재시작, 로컬 타임존 변경, 파일 이동, 복수 JSON 파일 및 오프라인 상태를 테스트.

**자동화 모드**: 초기 운영은 안전을 위해 승인 대기 기본값. 검증된 신뢰 클라이언트에 한해 생성 요청 자동 승인/처리 기능을 나중에 켤 수 있도록 정책 계층 분리. 삭제 자동 승인은 별도 고위험 옵션으로 취급.

## 6. 내부 이벤트 모델 및 JSON 호환성

외부 JSON 스키마를 지금 고정하지 않는다. 먼저 변환 계층의 계약을 정의한다.

| 내부 필드(가칭) | 의미 | 참고 |
| --- | --- | --- |
| source_id | 클라이언트 원본 일정 고유 ID | 중복 방지를 위해 필요, 실제 매핑 TBD |
| summary | 제목 | 필수 |
| start_at / end_at | 시작/종료 | ISO 8601 + timezone 등 입력 규칙 추후 확정 |
| all_day | 종일 여부 | 선택 |
| location | 장소 | 선택 |
| description | 내용 | 선택 |
| attendees[] | 참석자(이름/이메일 등) | 필드 형태 TBD |
| memo | 메모 | 비공개 저장/표시 정책 TBD |
| source_version | 원본 업데이트 버전 | 가능하면 수집 |
| deletion_marker | 삭제 의도 | 실제 JSON 형식 협의 후 확정 |

변환 모듈 인터페이스(개념):

~~~text
JsonSourceAdapter
  detect(file) -> format/version
  validate(file) -> validation result
  normalize(file) -> list[CanonicalEvent]
  extract_deletions(file, previous_snapshot) -> explicit delete intents
~~~

- 입력 JSON의 배열/객체 구조, 필드명, 날짜 형식, 파일당 이벤트 수, 파일 인코딩, 수정/삭제 방식은 **미정**.
- 필드 누락 및 알 수 없는 속성은 명확히 보고하고 원본은 변경하지 않는다.
- 포맷이 바뀌어도 Google 연동/요청 워크플로에는 영향이 없도록 Adapter를 독립 모듈로 둔다.

| HTTP | 경로 | 역할 |
| --- | --- | --- |
| GET | /api/v1/calendar/events | 지정된 캘린더의 허용된 이벤트 조회 |
| POST | /api/v1/requests/create | 신규 일정 생성 요청 |
| POST | /api/v1/requests/delete | 기존 이벤트 삭제 요청 |
| GET | /api/v1/requests/{request_id} | 접수/승인/실행 결과 |
| GET | /api/v1/admin/requests | 관리자 대기 목록 |
| POST | /api/v1/admin/requests/{request_id}/decision | 승인/거절 |
| POST | /api/v1/agent/batches | 데스크톱 변경분 일괄 수신 (조건부) |
| GET | /api/v1/agent/batches/{batch_id} | 일괄 처리 결과 |

- API 권한은 **일반 접속자 / 관리자 / 등록된 Agent**로 분리.
- 등록·전송 API는 인증된 주체, 대상 calendarId, eventId 소유 범위를 모두 확인.
- 모든 변형 요청은 request ID, idempotency key, 상태, 생성/승인/실행 시간, actor를 기록.
- 예상 상태: PENDING → APPROVED/REJECTED → EXECUTING → SUCCEEDED/FAILED/CONFLICT.
- 충돌 상태는 기존 이벤트 변경, 타 접속자 선처리, 동일 source_id 중복 등으로 구분.
- 사용자 API 호출은 일정 생성 성공을 즉시 가정하지 않으며 처리 상태를 조회할 수 있어야 함.

## 8. 기술 스택 (초기 제안)

- Backend: Python + FastAPI + Pydantic (OpenAPI 자동 명세 및 검증)
- Google 연동: Google Calendar API 공식 클라이언트
- DB: PostgreSQL (운영), SQLite (개발/로컬 테스트)
- 웹 UI: TypeScript + React 또는 서버 렌더링 중심의 경량 UI; **Menlo 호환성 실측 후 선택**
- Agent: Python 기반 백그라운드 서비스/트레이 앱 + 파일 감시 및 주기적 재스캔. 배포 대상 OS 확인 후 PyInstaller 또는 네이티브 서비스 선택.
- 배포: HTTPS 리버스 프록시 + 컨테이너 배포(허용되는 환경인 경우)
- Test: pytest + API 통합 테스트 + 브라우저 E2E + Agent 시뮬레이션
- 관측: 구조화 로그, 상관관계 ID, 오류 알림, 감사 로그

특정 프레임워크/운영 환경은 확정이 아니다. 우선 **Menlo 네트워크 접근 검증과 배포 OS 확인**이 필요하다.

## 9. 개발 단계와 산출물

| 단계 | 목표 | 산출물 / 완료 조건 |
| --- | --- | --- |
| Phase 0. 환경 및 정책 검증 | Menlo / Google API / Agent 경로 타당성 | 실접속 테스트, 승인된 네트워크 흐름, 접근 권한 확정 |
| Phase 1. Calendar Read MVP | 지정 캘린더 읽기 및 조회 UI | 인증, 조회 화면, 캘린더 고정, 기본 캐시/동기화 |
| Phase 2. 요청 워크플로 | 생성/삭제 요청 및 승인 | 검증, 작업 큐, 상태 조회, 중복 방지, 감사 로그 |
| Phase 3. JSON Agent 프로토타입 | JSON 감시와 전송 프로토콜 | Adapter 계약, 테스트 fixture, 전송 큐, 모의 데이터 연동 |
| Phase 4. 실제 JSON 연동 | 제공된 샘플 JSON 연결 | 실제 파서/매핑, 신규/삭제 시나리오, 사용자 UAT |
| Phase 5. 배포 안정화 | 운영 품질 및 보안 | 설치 패키지, 운영 문서, 복구/장애 대응 및 테스트 |

**권장 구현 순서:** 정책 확인 → 웹에서 단일 캘린더 조회 → 수동 생성/삭제 요청 → 승인 후 실제 반영 → Agent 모의 JSON → 실제 JSON 어댑터.

## 10. 시험 및 인수 기준

- [ ] Menlo 경유 접속으로 조회와 생성/삭제 요청을 정상 제출할 수 있다.
- [ ] 접속자가 URL/API 파라미터를 바꾸더라도 허가되지 않은 캘린더는 조회/변경할 수 없다.
- [ ] 생성 요청의 제목·시작/종료·장소·내용·참석자·메모가 정의된 매핑 규칙대로 처리된다.
- [ ] 생성/삭제 요청의 승인/거절/실패 결과를 추적할 수 있다.
- [ ] 승인되지 않은 삭제 요청은 Google Calendar에서 실행되지 않는다.
- [ ] 삭제 직전 이벤트 변경 또는 권한 변경이 감지되면 충돌 처리한다.
- [ ] 동일 요청을 두 번 보내거나 네트워크 장애 뒤 재시도해도 일정이 중복 생성되지 않는다.
- [ ] 잘못된 JSON, 빈 파일, 잠깐 사라진 파일이 대량 삭제를 유발하지 않는다.
- [ ] Agent가 오프라인 이후 재연결되면 미전송 요청을 안전하게 재처리한다.
- [ ] Google Calendar API pagination, syncToken 갱신, HTTP 410, API 429/5xx를 테스트한다.
- [ ] 로그/DB에 불필요한 참석자 정보·인증 비밀이 남지 않는다.
- [ ] 정책상 Agent API 접근이 불가능하면 자동 동기화가 비활성화되고 명확한 오류를 표시한다.

## 11. 결정 대기 항목 (추후 확인)

1. **Menlo 환경:** 정확한 접속 경로/구성, SSO, 접근 통제, POST·파일 업로드 허용 여부.
2. **에이전트 네트워크:** 브라우저 이외의 승인된 자동 API 연결 경로 존재 여부. 가장 큰 구현 선결조건.
3. **사용 환경:** Windows/macOS/Linux, 설치 권한, 상시 실행 가능 여부.
4. **Google Calendar:** 개인 Gmail 또는 Workspace, 인증 주체, 허가된 calendarId, 표시/쓰기 권한.
5. **사용자 정책:** 접속자별 조회 범위, 생성 즉시 반영/승인, 다른 사람 일정 삭제 요청 허용 여부.
6. **JSON 사양:** 샘플, 인코딩, 파일 경로/개수, 일정 ID, 시간 형식, 삭제 표시 방식, 갱신 주기.
7. **메모의 의미:** Google Calendar 설명으로 공개할지, 작성자/관리자에게만 보이는 내부 메모인지.
8. **참석자:** 이메일 필드와 초대 메일 발송 정책, 외부 수신 허용 여부.
9. **운영 환경:** 호스팅/도메인/인증서, DB, 로그 보존 기간 및 백업.
